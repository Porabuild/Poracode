# Versioned State & Protocols

A compatibility boundary is any shape or behavior that one side writes and
another side reads across a process restart, an app upgrade, a process or machine
hop, or an independently updated component: persisted state, caches and derived
indexes, serialized manifests, wire and IPC protocols, and deployed helpers or
plugins. These boundaries matter because older artifacts outlive the code that
wrote them: a database, cache file, staged helper, paired phone, or long-lived
browser tab from a previous release will meet the new code. Every change to a
boundary needs an explicit decision about what happens to those artifacts.

## Required check for every change

Before finishing work that changes data produced or consumed across restarts, app
versions, processes, machines, or independently updated components:

1. Identify every writer, reader, persisted copy, mirrored cache, and deployed
   copy of the changed shape or behavior. Follow the value end to end, not just
   the file you edited.
2. Decide whether old data or artifacts are still valid. Optional TypeScript
   fields do not make derived data semantically current.
3. Choose one outcome:
   - **Still valid:** keep the version and add backward-compatible parsing where
     needed.
   - **Migratable without loss:** bump the version and add an ordered migration.
   - **Derived or disposable:** bump the version and invalidate it so it is
     recomputed.
4. If the change crosses a wire or deployed-component boundary, update
   compatibility ranges and every producer and consumer together. Preserve older
   versions when practical; when not, reject the old peer with a typed error
   instead of half-working.
5. Add a regression test that starts from the previous released version or shape.
   A clean-profile test is not enough.
6. Search for duplicated or mirrored versions before stopping:

   ```sh
   rg -n --hidden --glob '!node_modules' --glob '!dist' --glob '!out' \
     '(SCHEMA_VERSION|CACHE_VERSION|PROTOCOL_VERSION|STORE_VERSION|MANIFEST_VERSION|FORMAT_VERSION|BRIDGE_VERSION|version: [0-9]+|schemaVersion|formatVersion)'
   ```

Version bumps follow compatibility, not code churn. A change that keeps every old
artifact valid needs no bump, but it still needs the audit.

## Recording decisions

Record the reason for a version, or for deliberately not bumping one, in a comment
beside the version constant or migration and in the PR description, so the next
change can apply the same reasoning without re-deriving it.

Do not append per-change narrative to this file. Update the inventory below only
when a boundary is added, removed, or moved. The pre-2026-10-14 narrative log is
archived in [`docs/versioning-history.md`](../../docs/versioning-history.md); it is
unmaintained and not needed for routine work.

## Boundary rules

- **Mirrored layers move together.** Some state has several durable copies, such
  as the agent-status path (provider probe, supervisor cache, IPC, renderer
  persisted store, UI). An old value can survive in any layer, so audit every
  layer's version and test each with a previous-version fixture.
- **Reserved numbers stay reserved.** Some constants document skipped or reserved
  versions in the comment beside them; read it before choosing the next number,
  because a reserved number may already be claimed by an unmerged branch.
- **Unknown future versions are refused, never rewritten.** A reader that meets a
  newer format preserves the bytes and fails closed, because downgrades and mixed
  installs are real.
- **Additive within a version is allowed only when old readers stay correct:** new
  optional fields that old readers ignore, new discriminators that old peers
  reject before any effect, or capabilities that are negotiated before use.
- **Derived values are regenerated, not quoted.** Hashes, fingerprints, and
  generated manifests come from their generators; do not hard-code their current
  values in docs.
- **Credential and custody stores are never invalidated like caches.** Migrate
  them, and delete a legacy slot only after the new one is durably written.
- **External protocol identifiers** (MCP protocol dates, ACP SDK protocol
  versions) are negotiated standards, not Poracode generations. Change them only
  with the dependency upgrade and interoperability tests.
