# Versioned State & Protocols

A compatibility boundary is any shape or behavior that one side writes and
another side reads across a process restart, an app upgrade, a process or machine
hop, or an independently updated component: persisted state, caches and derived
indexes, serialized manifests, wire and IPC protocols, and deployed helpers or
plugins. These boundaries matter because older artifacts outlive the code that
wrote them: a database, cache file, staged helper, paired phone, or long-lived
browser tab from a previous release will meet the new code. Every change to a
boundary needs an explicit decision about what happens to those artifacts.

## Required check for every change

Before finishing work that changes data produced or consumed across restarts, app
versions, processes, machines, or independently updated components:

1. Identify every writer, reader, persisted copy, mirrored cache, and deployed
   copy of the changed shape or behavior. Follow the value end to end, not just
   the file you edited.
2. Decide whether old data or artifacts are still valid. Optional TypeScript
   fields do not make derived data semantically current.
3. Choose one outcome:
   - **Still valid:** keep the version and add backward-compatible parsing where
     needed.
   - **Migratable without loss:** bump the version and add an ordered migration.
   - **Derived or disposable:** bump the version and invalidate it so it is
     recomputed.
4. If the change crosses a wire or deployed-component boundary, update
   compatibility ranges and every producer and consumer together. Preserve older
   versions when practical; when not, reject the old peer with a typed error
   instead of half-working.
5. Add a regression test that starts from the previous released version or shape.
   A clean-profile test is not enough.
6. Search for duplicated or mirrored versions before stopping:

   ```sh
   rg -n --hidden --glob '!node_modules' --glob '!dist' --glob '!out' \
     '(SCHEMA_VERSION|CACHE_VERSION|PROTOCOL_VERSION|STORE_VERSION|MANIFEST_VERSION|FORMAT_VERSION|BRIDGE_VERSION|version: [0-9]+|schemaVersion|formatVersion)'
   ```

Version bumps follow compatibility, not code churn. A change that keeps every old
artifact valid needs no bump, but it still needs the audit.

## Recording decisions

Record the reason for a version, or for deliberately not bumping one, in a comment
beside the version constant or migration and in the PR description, so the next
change can apply the same reasoning without re-deriving it.

Do not append per-change narrative to this file. Update the inventory below only
when a boundary is added, removed, or moved. The pre-2026-10-14 narrative log is
archived in [`docs/versioning-history.md`](../../docs/versioning-history.md); it is
unmaintained and not needed for routine work.

## Boundary rules

- **Mirrored layers move together.** Some state has several durable copies, such
  as the agent-status path (provider probe, supervisor cache, IPC, renderer
  persisted store, UI). An old value can survive in any layer, so audit every
  layer's version and test each with a previous-version fixture.
- **Reserved numbers stay reserved.** Some constants document skipped or reserved
  versions in the comment beside them; read it before choosing the next number,
  because a reserved number may already be claimed by an unmerged branch.
- **Unknown future versions are refused, never rewritten.** A reader that meets a
  newer format preserves the bytes and fails closed, because downgrades and mixed
  installs are real.
- **Additive within a version is allowed only when old readers stay correct:** new
  optional fields that old readers ignore, new discriminators that old peers
  reject before any effect, or capabilities that are negotiated before use.
- **Derived values are regenerated, not quoted.** Hashes, fingerprints, and
  generated manifests come from their generators; do not hard-code their current
  values in docs.
- **Credential and custody stores are never invalidated like caches.** Migrate
  them, and delete a legacy slot only after the new one is durably written.
- **External protocol identifiers** (MCP protocol dates, ACP SDK protocol
  versions) are negotiated standards, not Poracode generations. Change them only
  with the dependency upgrade and interoperability tests.

## Inventory

### Controlled CLI request interaction

`HOST_ADMIN_V22_VERSION` in `src/shared/hostAdminProtocol.ts` adds a closed,
opt-in preparation wrapper and run-scoped pending-request read/respond commands.
`HOST_ADMIN_V23_VERSION` requires supervisor request-incarnation custody for new
interactive callers. `HOST_ADMIN_V24_VERSION` adds an opt-in run-preparation
wrapper for JSON tool events. Versions 1-23 retain their exact closed schemas and
echoed versions; accepted v22 callers also use the corrected supervisor custody.
An older owner rejects v24 before preparation effects, and the CLI falls back to
the prior preparation only for the typed unsupported-operation refusal. New
owners emit tool records only for v24 opt-ins; v15-v23 callers keep the legacy
stream. `HOST_RUN_FORMAT_VERSION` 1 remains for legacy streams and options;
`HOST_RUN_TOOL_EVENT_FORMAT_VERSION` 2 identifies the opt-in tool stream. Text
output, outer host-control operations/capabilities and public remote routes stay
unchanged.

`CONTROLLED_THREAD_REQUEST_VERSION` in `src/shared/contracts/threadExecution.ts`
versions the distinct supervisor-only `controlledThreadRequest` qualify/read/respond
procedure. Version 2 binds the displayed request to a supervisor-issued incarnation
token and rechecks it immediately before dispatch. Qualification precedes provider
launch; old supervisors loud-refuse the name or version. Version 1 and future
versions refuse without launch or reply effects. Replies require the execution
operation, thread, live request ID and token;
cancelled/resolved/duplicate requests refuse, and retirement joins outstanding
reply promises after process close. Existing control/reservation version-1
contracts, hop 18 and remote 14 stay unchanged under additive-name compatibility.
Regenerate the local procedure inventory and fingerprint canonically. No database,
settings, credential or deployed-helper format changes are required.

Current values live in the referenced constants; read them rather than relying on
numbers in prose. Paths are relative to the repository root; a bare file name sits
beside the file named earlier in the same row.

### Wire and IPC protocols

Local project administration uses closed inner admin v14, with project inventory JSON format1 (`src/shared/contracts/hostProjects.ts`). Prior admin1–13 shapes and echoes remain unchanged; old/future owners refuse before writes. Project pages reuse the existing versioned catalog inventory cursor. No outer operation, public remote protocol, persisted schema or credential format changes.

Selected native provider reads use supervisor-only probeSelectedAgent with closed version1 request/result (src/shared/contracts/agent.ts). Old supervisors reject the distinct procedure name; future versions and unknown fields refuse before probing. Replies echo the exact provider and native environment. This read never writes or publishes discovery cache state or schedules automatic installation; existing cache versions and full discovery behavior are unchanged. The additive local procedure refreshes the hop18 fingerprint only; public remote allowlists and schemas remain unchanged.

Custom native ACP registration uses closed local admin v16 (HOST_ADMIN_V16_VERSION in src/shared/hostAdminProtocol.ts), with closed CUSTOM_ACP_AGENTS_VERSION1 commands and JSON metadata (src/shared/contracts/customAcpAgents.ts). Earlier admin1–15 schemas and echoes remain unchanged; old/future envelopes refuse before effects. Every write is computed from the settings authority’s fresh CAS snapshot; same-target revision changes refuse. Existing generic instances, native command scoping and sealed provider environment storage are reused without a settings/DB/cache migration. No supervisor RPC, procedure-map pin, public remote route, outer capability or credential domain changes.

### Test and QA formats

`DESKTOP_HOST_CONTROL_VERSION = 1` in `src/shared/desktopHostControl.ts`.
Its closed schema and exact version/generation acknowledgement gate main and
backend together; unsupported or foreign acknowledgements refuse before
supervisor startup. Future grants refuse before key/database/service effects.
Older initialize payloads without the grant retain their previous behavior.
This additive opt-in does not change the hop envelope, existing local-admin
unions, host-control/discovery versions, capabilities, or public remote routes.

in `src/server/cliLogs.ts`: NDJSON `{formatVersion, view:"local-log", kind,
text}`. It does not alter log-file storage, local host administration, or any
public transport. Completion query v1 retains its existing shape; the new
static command/flag candidates are valid for existing consumers.
